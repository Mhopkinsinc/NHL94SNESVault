SNES Music And Organ Notes

Overview

The SNES game does not use the Genesis-style 5-byte per-team music table.
The in-game music path is split into:

1. A per-team organ music pointer table.
2. A separate shared goal-music pool.

The main music player entry point is CODE_80A2E0 / fn_PlayMusic at $80A2E0.
The caller passes a music data pointer in $0C/$0E.


General Music Entry Points

Main Menu Music
Caller: CODE_9F82FB
Setup:
											 LDA.W #$0090                         ; bank byte -> $0E
											 STA.B $0E
											 LDA.W #$C20C                         ; pointer low word -> $0C
											 STA.B $0C

Intro Music
Caller: $9DB2AD
Setup:
											 LDA.W #$008F
											 STA.B $0E
											 LDA.W #$DD32
											 STA.B $0C

Finals Playoff Music
Caller: $9D8BEF
Setup pattern:
											 LDA.W #$0093
											 STA.B $0E
											 LDA.W #$31ED
											 STA.B $0C


In-Game Team Music Selector

Routine: CODE_9C9B5F in bank_9C

Purpose:
- Chooses per-team organ music from a table in bank_80.
- Falls back to shared goal music if the selected table entry is disabled.

Early exit:
- If $07F3 is nonzero, the routine returns immediately without starting new music.

Effective index math:
- Input A is the slot number.
- Team ID comes from $1C98.
- The routine computes:

	X = ((team_id * 6) + slot) * 4

This means the per-team organ table is organized as 6 slots per team, with each
slot consuming 4 bytes.

Why this is 6 slots and not 3:
- The table region from $80DA56 to $80DCF6 is 672 bytes total.
- 672 / 4 = 168 pointer entries.
- 168 / 28 teams = 6 entries per team.


Per-Team Organ Table

Effective table region:
- Low word starts at $80DA56.
- Bank/high bytes are read from $80DA58.

The disassembly labels are split, but the routine treats them as one 4-byte-entry
table:

- LDA.L UNREACH_80DA58,X -> loads the bank/high portion into $0E
- LDA.L UNREACH_80DA56,X -> loads the low word into $0C

Important detail:
- If the byte read from UNREACH_80DA58,X is negative ($FF), the organ entry is
	treated as disabled and the code branches to goal-music fallback.

Observed table size:
- $80DA56 .. $80DCF5
- 672 bytes
- 168 entries
- 28 teams x 6 slots x 4 bytes


Goal Music Fallback

Routine path: CODE_9C9B8B

If the selected organ slot is disabled, the code does not try another team slot.
Instead it chooses a random entry from the shared goal-music pool:

- Base table: UNREACH_80DCF6 / UNREACH_80DCF8
- Random selector source: CODE_9BB385 with A = #$0008

This goal-music pool is global and is not indexed by team.


Live Slot Requests In Vanilla Code

The only live call site into CODE_9C9B5F is in bank_9F around $9FA8BA-$9FA909,
but that block requests multiple slot values.

Confirmed requests:

1. Slot 4
	 Raw bytes at $9FA8D1 decode to:
	 - LDA.W #$0004
	 - JSL.L CODE_9C9B5F
	 This path runs when the high nibble of $1624 is less than the low nibble.

2. Slot 1
	 Normal assembled path at $9FA8DA:
	 - LDA.W #$0001
	 - JSL.L CODE_9C9B5F
	 This path runs when the high nibble of $1624 is greater than or equal to the
	 low nibble after the unequal-nibble test.

3. Slot 2
	 Raw bytes at $9FA902 decode to:
	 - LDA.W #$0002
	 The call at $9FA905 then uses that value when $0CC1 is zero.

4. Slot 0
	 At $9FA8FA the routine loads:
	 - LDA.W #$0000
	 That value is used by the call at $9FA905 when $0CC1 is nonzero.

So the currently observed vanilla slot usage is: 0, 1, 2, and 4.
Slots 3 and 5 exist in the table layout but are not yet proven as live from the
call sites checked so far.

Quick observations from the map:
- Slot 4 is heavily shared. $9A:B2DF appears in 22 team rows.
- ANH, FLA, ASE, and ASW are fully disabled in the current table.
- SJ is the only team in this decode with all 6 slots populated.
- Slots 3 and 5 are populated for some teams even though live slot requests for
	those positions are not yet confirmed from the caller analysis.


Selector State Feeding The Slot Choice

$1624
- This value is split into high and low nibbles at $9FA8BA-$9FA8CB.
- If the nibbles are equal, execution falls through to the slot-0/slot-2 logic.
- If the nibbles differ, execution chooses slot 4 or slot 1.

Penalty-related code writes $1624 in multiple places, including:
- bank_9E around $9EBEEE, where the value is incremented.
- bank_9F around $9FCDC9, where the value is incremented/decremented.
- bank_9F at $9FCDFA contains an in-code note: PenCalled 5th (in the box).

$0CC1
- Initialized to $FFFF at $9F84C3.
- Sometimes cleared at $9F84E8.
- Later consumed at $9FA8E3 and $9FA8FD to decide whether the selector call uses
	slot 0 or slot 2.
- Cleared again after the call at $9FA909.


Worked Example

Example pointer load for team music:
- Team ID from $1C98 = t
- Requested slot = s
- Entry offset = ((t * 6) + s) * 4
- Bank byte comes from $80DA58 + offset
- Low word comes from $80DA56 + offset
- fn_PlayMusic is called with the resulting pointer in $0C/$0E


Expansion Notes

The current SNES baseline for future expansion is:
- 28 teams
- 6 organ slots per team
- 4 bytes per slot
- separate shared goal-music pool

Before relocating or extending the table, the next reverse-engineering tasks are:
- Rename the anonymous UNREACH_80DA56 / UNREACH_80DA58 labels to explicit organ
	table labels.
- Map each of the 6 slot positions for every team.
- Determine whether slots 3 and 5 are dead, unused in vanilla, or reached through
	code not yet documented.
- Audit any hard-coded team-count assumptions before changing table size.


Open Questions

- What human-friendly gameplay names correspond to slots 0, 1, 2, 3, 4, and 5?
- Are slots 3 and 5 reachable in normal gameplay, or only reserved in the table?
- Does $0CC3, which receives slot+1 at the end of CODE_9C9B5F, affect later music
	suppression or repeat logic elsewhere?
